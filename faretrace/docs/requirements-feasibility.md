# 需求与可行性分析 — FareTrace 网约车透明账单归因系统

> 对应实验手册第一部分第 1 项（需求与可行性分析，10%）。
> 引用格式：哈佛（Harvard）引用格式，文献列表见 `docs/references.md`。
> 项目定位：**面向网约车/出行科技平台账单流程的、基于信息系统的流程改进提案**。小组情境：成员拟申请出行平台数据分析 / 系统架构 / 运营优化岗位，故选择这一"感兴趣且希望不久将来从事"的业务流程作为分析对象。

## 1. 业务背景与关键问题

### 1.1 业务流程现状（As-Is）

网约车订单的资金链路同时存在四路数据：**预估价快照**（下单时生成）、**实付账单**（行程结束后生成）、**实际行驶轨迹**（GPS 上报）与**参考路径**（平台预估时使用的规划路线）。现有系统只向乘客和司机输出两个数字——"预估价 18 元"与"实付 27 元"，中间的差额由客服以"系统按实际里程和时长计算"一句话带过。

### 1.2 关键问题（Problem Statement）

| 编号 | 问题 | 证据/来源 |
|---|---|---|
| P1 | 预估价与实付价偏差缺乏解释：乘客不知道多付的钱对应哪段路、哪段时间 | 广东省消委会调查显示部分网约车样本实际用时明显大于预计用时（Guangdong Consumers Council, 2024） |
| P2 | 扣款依据不可举证：司机被平台扣款后无法自证清白，争议处理依赖客服主观判断 | 交通运输部新规强调网约车计价规则公开、账单可追溯（Ministry of Transport, 2023） |
| P3 | 聚合平台派单方与实际承运方不一致、上车点偏移等问题加剧信任损耗 | 媒体调查报道聚合打车模式下的账单争议案例（Xinhua News Agency, 2024） |
| P4 | 平台内部数据孤岛：预估、账单、轨迹、路径四路数据已存在，但缺少把它们组织成"面向当事双方的透明账单"的归因层 | 平台公开 API 文档仅提供订单金额字段，无差额构成接口（Didi Chuxing, 2023） |

### 1.3 解决方案（To-Be）

构建独立的**费用差额归因层（FareTrace）**：订单完成后自动读取四路数据，用规则化三维偏差分解（距离、时间、价格规则/杂费）把总差额拆成六个可解释归因项，每项附业务说明与证据 JSON；面向乘客输出"预估价到实付价的差额构成"，面向司机输出"哪些差额与驾驶行为相关、哪些与路况或计价规则相关"；任一方可对单项发起争议，系统冻结证据快照供运营复核。系统**不做责任裁决**，只把"差额从哪里来、证据是什么"结构化呈现，让争议有据可查。

### 1.4 用户群体与利益相关者

| 利益相关者 | 痛点 | 系统为其提供什么 | 参与方式 |
|---|---|---|---|
| **乘客** | 不知道多付的钱去了哪里，投诉无门 | 逐项差额构成 + 可展开的时间段/轨迹片段/字段对比证据 | 查看透明账单、发起争议 |
| **司机** | 被扣款却无法自证；早晚高峰堵车被误认为绕路 | 司机视角分组（驾驶行为相关 / 路况 / 平台规则），免责证据 | 查看扣款依据、发起争议 |
| **平台运营/仲裁人员** | 客服凭口头解释处理争议，效率低、易升级 | 冻结的证据快照、结构化归因记录、状态机复核 | 复核争议、流转状态 |
| **监管方** | 计价不透明、账单不可追溯是投诉热点 | 归因记录含规则版本与阈值口径，满足"计价公开、可追溯"监管要求 | 抽查审计（只读） |
| **平台业务方** | 差额争议消耗客服成本、影响 NPS | 差额构成的结构化数据，可反哺预估价与客服知识库 | 消费归因统计 |

### 1.5 需求概述（功能/非功能）

**功能需求**（详见 `docs/system-design.md` 与 `docs/use-cases.md`）：

- FR1 订单数据接入：预估价快照、实付账单、实际轨迹（允许缺失/畸形）、参考路径；
- FR2 差额归因：规则化三维偏差分解，六归因项 + 残差显式保留，金额守恒 ±0.01 元；
- FR3 透明账单：乘客/司机双视角，每项证据可展开，数据质量降级明示；
- FR4 争议与证据回溯：发起即冻结快照，状态机 OPEN→REVIEWING→RESOLVED/REJECTED；
- FR5 口径可追溯：阈值/规则版本集中配置，归因记录落库 `config_version`，接口只读查询；
- FR6 模拟数据演示：六类种子订单覆盖正常/拥堵/绕路/规则变化/残差/降级。

**非功能需求**：

| 类别 | 要求 | 实现与验证 |
|---|---|---|
| 可靠性 | 畸形轨迹（空/乱序/重复/瞬移/同刻/缺口）不崩溃，降级并留痕 | 12 项轨迹预处理测试 + 质量标记枚举 |
| 可审计性 | 每个归因项附证据 JSON（时间段、轨迹片段、阈值、规则版本、计算公式） | `evidence_json` 结构化字段，`GET /api/orders/{no}/attribution` |
| 一致性 | 归因项之和 + 残差 = 总差额（±0.01 元） | Decimal 计算 + 36 组随机订单守恒测试 |
| 确定性/幂等 | 同输入同配置结果一致；重算不产生重复记录 | 确定性测试 + `revision` 递增 + 唯一约束 |
| 可用性 | 一键运行、无外部依赖 | SQLite + 零外部 API；`pip install -r requirements.txt && uvicorn` |
| 隐私合规 | 演示数据无个人信息；真实落地需符合个保法/数安法 | 合成数据声明 + 第 6 节法律可行性 |

## 2. 可行性分析（TELOS）

### 2.1 技术可行性（T）

- **数据可得**：预估价快照、实付账单、轨迹点、参考路径在平台侧均已存在（P4），本系统只需要读取，不需要新增采集硬件。
- **算法成熟**：核心是"字段对比 + 规则计算 + 几何投影"，无机器学习依赖。轨迹投影用 shapely 在局部等距平面完成，城市尺度误差 < 0.5%（已用已知折线单元测试验证）；三维分解用 Decimal 逐项计算，金额在 ±0.01 元内严格闭合（73 项自动化测试含 36 组随机订单守恒验证）。
- **实现工作量可控**：课程团队按 `TEAM_ROLES.md` 六角色分工，后端 + 算法约 1,800 行 Python，两周内可交付（进度可行性部分给出甘特估算）。
- **技术风险与对策**：GPS 漂移导致误判绕路 → 以"拟合度门控 + 偏离段证据"呈现而非直接定性；轨迹缺失 → 降级口径显式标记（`ASSUMPTIONS.md` B6），不静默补充。

**结论：技术上可行。**

### 2.2 经济可行性（E）

成本/效益分析（课程演示规模，单位：人日与相对成本）：

| 项目 | 估算 | 说明 |
|---|---|---|
| 开发成本 | 约 18 人日（后端 5、算法 5、前端 2、文档 4、测试与联调 2） | 课程团队内部消化，无现金支出 |
| 运行成本 | 接近 0：SQLite 单文件 + 单进程 Uvicorn，演示机即可承载 | 无云服务、无地图 API 计费 |
| 预期收益 | ① 客服争议处理时长下降（每单差额争议从"人工调四路数据"变为"看一份结构化账单"）；② 争议率下降（乘客/司机能看懂扣款依据）；③ 监管合规成本下降（账单可追溯已是监管要求） | 行业报告估计网约车平台订单相关投诉中账单类占比可观（iiMedia Research, 2024） |
| 投资回收期 | 课程范围内以"演示即交付"衡量；若真实落地，按客服人力节约估算，边际成本低 | 本项目不承诺精确 ROI，避免伪造财务数据 |

敏感性提示（对应手册财务可行性要求）：若轨迹数据质量低于假设（缺失率 > 40%），降级账单比例上升，归因说服力下降 → 需求侧应优先保障轨迹上报质量；若监管收紧要求更强审计字段，需追加"归因记录不可篡改"存储（见 2.3）。

**结论：经济上可行（课程范围内零边际成本，真实落地收益以流程效率为主）。**

### 2.3 法律可行性（L）

- **个人信息保护**：轨迹属于个人行踪信息，受《个人信息保护法》约束（Standards Press of China, 2021）。本项目演示数据全部合成，起点/终点为"某小区/某写字楼"级别标签，无精确住址，不可反推真实位置。
- **数据安全**：演示库为本地 SQLite，不联网传输；真实落地时需加密存储、最小化留存期限、争议举证时脱敏。
- **监管合规**：交通运输部新规要求网约车平台公开计价规则、账单可追溯（Ministry of Transport, 2023），本系统的 `config_version` + 归因记录落库设计正是对该要求的直接响应，属于"合规增益"而非合规风险。
- **责任边界**：系统明确不做责任裁决（页面与接口均带免责说明），归因结果定位为"待复核证据"，避免系统输出被误用为处罚依据。

**结论：法律上可行，且对现行监管方向有正向支撑。**

### 2.4 运营可行性（O）

- **与现有流程契合**：归因层不替代平台计价、不接入支付，只在订单完成后追加一步计算，对现有业务流程侵入极小。
- **期望运营成果**（对应手册"可靠性、可维护性、可支持性、可用性、可生产性、可处置性、可持续性、可负担性"）：可靠性（畸形输入降级不崩）、可维护性（阈值外置 yaml、模块分层清晰）、可支持性（统一错误结构 + 只读配置接口便于排障）、可用性（一键运行、三页面朴素易用）、可生产性（种子脚本可重复生成演示数据）、可处置性（删除 `faretrace.db` 即完全卸载数据）、可持续性（口径版本化，规则演进不破坏历史争议证据）、可负担性（零外部服务成本）。
- **文化契合**：乘客与司机获得"看得懂的账单"，运营从"凭经验调解"转为"按证据复核"，方向上与平台公信力建设一致。

**结论：运营上可行。**

### 2.5 进度可行性（S）

| 阶段 | 内容 | 里程碑 |
|---|---|---|
| 阶段 1 | 结构、配置、模型、假设文档 | 建表与口径测试通过 |
| 阶段 2 | 轨迹/计价/归因核心 + 单元测试 | 守恒与场景测试全绿 |
| 阶段 3 | 接口 + 种子 + 端到端测试 | 全链路可运行 |
| 阶段 4 | 极简前端三页面 | 页面冒烟测试全绿 |
| 阶段 5 | 文档 + 全量验收 + 提交 | `pytest -q` 73 项通过 |

截止日期为课程第 13 周（周三），本项目按五阶段推进、每阶段以"测试全绿"为放行条件，估算总工作量 18 人日（团队 6 人并行约 1.5 周），**能在截止日期前完成，截止日期为期望性而非强制性约束下亦可提前交付**。

**结论：进度上可行。**

### 2.6 其他可行性（市场 / 资源 / 文化）

- **市场可行性**：账单透明是网约车投诉热点与监管重点，平台侧存在真实需求（P1–P3）；同类能力目前内嵌于各家平台客服工具，缺乏独立的"归因层"形态，课程原型具有演示与延伸研究价值（iiMedia Research, 2024）。
- **资源可行性**：所需资源为团队成员时间 + 一台本地机器，无外部依赖；不影响"正常业务运营"（本项目本身即独立演示系统）。
- **文化可行性**：透明账单对乘客与司机均为增量信息，无文化冲突；对平台内部客服流程是赋能而非替代。

## 3. 市场调研与分析（摘要）

- 需求侧：消委会与媒体调查显示预估/实付偏差、聚合平台派单与承运不一致等是高频投诉（Guangdong Consumers Council, 2024; Xinhua News Agency, 2024）。
- 供给侧：现有平台仅提供金额数字与客服话术，缺少"每一分钱配证据"的第三方可审计账单形态。
- 时机：监管新规强调计价公开与账单可追溯（Ministry of Transport, 2023），当前是引入归因层的合适窗口。
- 可行性研究报告输出：评估标准（TELOS 五维 + 守恒正确性）、研究结果（六类场景全部通过自动化测试）、建议（课程演示可交付；真实落地前需补齐路网级路径规划与真实路况源）。

## 4. 结论

TELOS 五维全部可行。本项目以零外部依赖、18 人日的成本，交付一个可运行、可演示、可审计的差额归因原型，直接回应"预估价 18 元、实付 27 元，双方都拿不到举证说明"的现实痛点。
